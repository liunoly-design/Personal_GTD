# PGTD 功能实现清单

更新：2026-09-27。基准提交：`6c8f258ecc341ba7dc6ded594756e20120394d31`。

本文件是功能编号、规划版本和推进状态的统一入口。[功能版本计划](功能版本计划.md)说明当前版本的业务边界与验收要求。本清单不自动授权实施所有候选功能。

## 如何使用编号

- “讨论 F103”：读取现有决定，只澄清影响该功能实现的问题。
- “给 F103 写规格”：用 to-spec 固化目标、边界、测试接口和验收步骤，保留未决项。
- “拆分 F103”：用 to-tickets 形成可独立演示的任务；过大时拆分，不按技术层交付。
- “开发 F103”：规格已明确则执行；否则先补齐必要决定，不重新询问已确认事项。
- “验收 F103”或“查看 V1 进度”：读取对应任务证据，区分模拟、真实接入和模型质量。

V0–V5 是路线图分组，不是 npm 发布版本；顺序可调整。F 编号永久保留，功能移到别的版本也不改号；取消时保留记录。新功能使用新编号，不能复用旧号。功能编号与单个开发任务编号不同，例如 F103 可以拆成 F103/T01、F103/T02。

状态说明：**已有**表示有运行实现，限制看证据；**待规格**表示功能方向已确认但实现/验收细节未冻结；**候选**表示需先决定是否纳入；**待验收**表示仍需补足证据。F101 的验证工具已交付，其余未完成项按各自状态推进。skill 或文档存在不等于业务功能已完成。

## 编号对应的 skill 开发流程

| 阶段 | 使用的本地 skill | 必须产生的结果 |
| --- | --- | --- |
| 讨论 | [grill-with-docs](../../.agents/skills/grill-with-docs/SKILL.md)，结合 [grilling](../../.agents/skills/grilling/SKILL.md) / [domain-modeling](../../.agents/skills/domain-modeling/SKILL.md) | 用户目标、已有决定、未决问题及原始问答；业务 OKR 访谈另用 personal-okr-discussion |
| 规格 | [to-spec](../../.agents/skills/to-spec/SKILL.md) | 当前单项规格：范围、输入输出、失败处理、测试接口、验收步骤、成本性能预算；未知数值明确标待测 |
| 拆任务 | [to-tickets](../../.agents/skills/to-tickets/SKILL.md) | 完整可演示的小任务及真实依赖；较大拆分先讨论粒度，不把所有候选项发布为 ready-for-agent |
| 实现 | [implement](../../.agents/skills/implement/SKILL.md) + [tdd](../../.agents/skills/tdd/SKILL.md) | 一个任务的行为测试先失败再通过，保留已有路径，运行相关示例 |
| 审查 | [code-review](../../.agents/skills/code-review/SKILL.md) | 默认单 agent 顺序审查规范和需求，包括本次未提交差异，处理阻塞发现 |
| 验收交付 | implement 的本地交付约定 | 适用完整检查、真实/模拟证据和限制、任务状态与验收勾选、仅本任务提交及授权范围内同步 |

采用 [本地 tracker](../agents/issue-tracker.md)：新功能资料放 `.scratch/f103-okr-session/` 这类带编号目录，规格为 `spec.md`，问答为 `discussion.md`，任务在 `issues/01-<slug>.md`。编号示例对应 F103/T01；任务写明 `Feature: F103`、`Blocked by:`、`Status:`、`State:`、验收项和 Verification。

发布规格/任务后，在本表的状态栏链接到具体文件；状态以任务证据为准。一个功能的所有必要任务验收完成才能标为已完成，取消或未验证部分须明示。既有 F001–F007 沿用原目录，不为统一编号搬迁历史。

Status 使用 needs-triage / needs-info / ready-for-agent / ready-for-human / wontfix；State 使用 open / in-progress / blocked / done。本清单的“待规格/候选”等是功能概览，不替代任务字段。尚无实现规格的条目不自动创建任务、不标 ready-for-agent。

本次采用 to-tickets 的完整路径与依赖原则整理清单，尚未发布实现 tickets；实际选定功能后再冻结拆分。已有明确的小改动可以直接实施，遵循项目约定，不强制重复采访。
