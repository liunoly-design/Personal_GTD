## 一手资料结论

### 1. 个人 OKR 需要明确目标和可核验的结果

What Matters 提供家庭与个人训练的 OKR 案例，强调具体、聚焦以及实现目标的路径。个人 OKR 不能只停留在愿望清单。[个人 OKR 案例](https://www.whatmatters.com/faqs/okrs-for-personal-life-goals-examples)

KR 可以衡量投入、产出或实际影响，也可以组合使用；应明确每种指标证明了什么，尽量关注最终改变。[KR 的三种类型](https://www.whatmatters.com/okrs-explained/input-output-outcome-key-results)

对 PGTD 的推论：完成若干关联任务不能自动证明 KR 达成。只有 KR 本身明确采用这些任务作为计量依据时，才可能按约定计算；否则需要用户补充结果证据。

### 2. 目标周期和检查频率可以不同

OKR 周期包括拟定、沟通、确定、跟踪、评分与反思。What Matters 建议根据上一周期学到的内容制定下一周期目标，避免年初预先锁死四个季度。[OKR 周期](https://www.whatmatters.com/okrs-explained/okr-cycle-phases)

周期内检查用于发现阻碍与调整行动；周期结束再评价结果与总结经验，两者用途不同。[检查与评分的区别](https://www.whatmatters.com/faqs/weekly-okr-grading-check-in)

对 PGTD 的建议：年度确定方向，季度确定当前重点，月度检查季度目标并调整项目与行动。月度 Review 不必生成独立的月度 OKR；如用户需要，再采用三层目标。该安排是个人产品适配，不是唯一标准。

### 3. 不同目标类型需要不同成功标准

What Matters 区分承诺型与挑战型目标：前者预期在周期内完整实现；后者允许跨周期推进。不能统一把所有目标达到 70% 当作成功。[目标类型](https://www.whatmatters.com/okrs-explained/committed-and-aspirational-okrs)

对 PGTD 的建议：先记录每项 KR 的成功条件与证据，不急于生成所有目标的综合分数。未知进展应显示待补证据，不能记为零或由模型猜测。

### 4. GTD 提供从目标到行动的承接层

GTD 官方的关注层级包括宗旨、愿景、目标、责任领域、项目和行动/日历。高层方向影响项目和行动，同时责任领域需要持续维护。[GTD 关注层级](https://gettingthingsdone.com/2018/12/the-gtd-horizons-of-focus-for-determining-your-priorities/)

对 PGTD 的建议：用“OKR → 项目 → 下一步行动”表达贡献关系；简单行动可以直接关联 KR。保留日常维护与暂不关联的事项，避免为了匹配 OKR 而强行归类。此映射是本项目设计建议，并非 GTD 官方定义的 OKR 集成方案。

## 建议的 Review 行为（待确认）

| 入口 | 核心讨论 | 保存结果 |
| --- | --- | --- |
| 年度 Review | 回顾年度结果和重要变化，决定下一年度方向与取舍 | 已确认年度目标、衡量标准、调整理由 |
| 季度 Review | 检查本季 KR 证据、有效行动与阻碍，选择下季重点 | 本季回顾、下季 OKR、项目和行动候选 |
| 月度 Review | 检查季度目标是否有进展，哪些项目需继续、调整或停止 | 本月证据、阻碍、下月重点与下一步行动候选 |

共同流程建议：读取目标及可用事实 → 缺少证据时提问 → 逐项讨论 → 展示修改内容 → 用户确认后保存。目标修改保留原值、时间与原因。Review 生成的候选行动仍需用户决定。

首次没有目标文件时，需要引导建立目标；不能把缺少历史记录解释为没有进展。手动启动与定时提醒的实现范围另行确定。

## Inbox 整理建议（待确认）

1. 读取一条真实 Inbox 事项与当前有效目标。
2. 澄清事项含义及是否需要行动。
3. 提出可能关联的 Objective/KR，并解释具体贡献；无法判断时询问。
4. 用户选择关联、日常维护或暂不关联；可修改建议。
5. 确认下一步行动与去向，再保存本次决定。

合成例子：季度目标为“形成可用于求职的作品集”，KR 为“完成两份案例，并各取得两位目标读者的反馈”。Inbox 中“整理旧项目截图”可关联该 KR，下一步建议为“选出一个项目的五张关键截图”。完成截图任务只证明该行动完成，不能自动把两份案例及反馈记为完成。

## 历史目标文件建议（已由 Apple 备忘录决定取代）

一个便于阅读和编辑的 Markdown 目标文件，保存稳定目标/KR ID、周期、目标说明、衡量标准、基线/目标值（适用时）、最新证据与日期、状态、关联项目和 Review 记录。周期结束保留历史，不覆盖成一份只有最新状态的文件。

文件保存目标及回顾，Apple 提醒事项仍提供实际任务状态；不得在文件里维护另一套权威完成状态。真实个人目标和回顾应保存在私有位置，代码仓库只放格式约定和合成样例。具体路径、与 Obsidian 的关系、手动编辑后的校验与冲突处理，在规格阶段确认。

## 当时的接续开发建议（最新顺序见功能版本计划）

先交付“小婕 gtd okr 讨论 → 第一轮背景提问 → 用户回复 → 保存私有讨论记录 → 暂停后续接”这一条完整路径，再扩展目标定稿、策略审视、Review 和 Inbox 关联。现有激活后默认收集规则会接收该表达，需在收集前增加明确的 OKR 路由，且保留普通收集语义。

下一项规格需确定私有文档位置、会话关联/退出语义、每轮上下文和模型预算。可观察验收应包含：启动讨论不创建 Inbox 事项；重复消息只记录一次；普通任务不携带 OKR 私人背景；重启后继续同一问题；保存失败不声称成功；用户未确认的目标仍为草案。这些是下一项开发建议，尚未标为可实施任务。

## 后续用户决定：Apple 备忘录独立模块

> OKR 记录在备忘录的一个文件内，然后和 reminder 通过标签关联，所以 OKR 讨论是随时可以讨论和回顾，如果有就相当于回顾，如果没有则新建。存放的位置就是在备忘录，然后备忘录也记录更新记录，所以做成一个独立模块。也写入功能版本计划中。重新列一下开发顺序。

已确定使用同一篇 Apple 备忘录保存目标、讨论和更新记录，并以标签关联提醒事项；不再以 Markdown 文件作为目标存储方案。已有记录进入回顾/续接，确认无记录才新建。具体账户、文件夹和标签能力仍需逐项验证。最新范围与依赖见 [功能版本计划](功能版本计划.md)。
