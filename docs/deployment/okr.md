# F103：OKR 日志记录与续接

## 已实现

可信飞书消息可启动、保存原文、暂停与续接固定的 Apple 备忘录。首次创建 `PGTD OKR 日志`，以后使用持久化的真实 ID。文本中的 `#O1`、`#KR1` 等标记原样保留。重复来源不重复写入；创建或追加响应未知时先核对外部记录，无法确认则停止。回执预览最多末尾 3000 字符，完整内容在备忘录。

F103 路径使用一篇日志。F104 已增加引导与确认后更新第二篇最新稿，见 [F104 说明](okr-finalize.md)；Review 分析、按原生提醒事项标签读取任务仍未实现。这里保存用户原文，不将其自动视为正式目标。备忘录内的 `#` 文本已经读回验证，未验证 Notes 的原生标签元数据。

## 启用后的用法

1. 发送 `小婕 gtd okr 讨论`，读取已有记录或首次建立日志。
2. 回复该回执，例如 `#O1 保持健康\n#KR1 每周运动三次`（实际输入可换行），保存讨论原文。
3. 也可发送 `小婕 gtd okr 记录：#KR1 本周运动两次`。需先启动当前会话。
4. `小婕 gtd okr 暂停` 停止记录；再次发送启动表达恢复。

普通未关联的聊天不写入 OKR；显式 GTD 收集请求继续走原有 Inbox 路径。未配置 OKR 时启动表达会提示未启用，不会误收集成任务。

## 配置

在插件 `runtimeConfigPath` 指向的私有 JSON 中增加以下字段（其余配置保留）：

```json
{
  "okr": { "account": "iCloud", "folder": "Notes" }
}
```

首次启动会在该位置创建日志，因此部署前须确认正式文档写入范围。也可增加 `noteId`，绑定用户明确指定的已有笔记。不要填 F101 合成测试 ID 作为正式文档。运行后不要删除 `stateDir/okr.sqlite` 或随意更换位置/ID；状态文件保存绑定、去重与待核对操作，不能靠删除它来处理冲突。

默认未启用；本轮没有修改运行网关配置、重启网关或发送真实飞书消息。真实环境仍须完成正式文档授权/配置与飞书端到端验收。原飞书身份、会话白名单和原消息校验继续适用。

## 验证命令

```bash
npm run test:okr
npm run demo:okr
npm run verify:okr -- --write-synthetic
```

最后一条会读取既有 `runtime/notes/probe.sqlite`，只复用 F101 已验证的合成笔记；追加两条固定合成记录并保留，重复运行复用同一 ID。可用 `--probe-state` 和 `--state-path` 指定私有状态路径。没有经过 F101 验证的合成笔记时停止，不创建正式文档。控制台只输出布尔证据、耗时和状态，不输出真实 ID 或正文。

## 验收与限制（2026-09-27）

- 飞书入口、关联回复、暂停/恢复、重复投递、重启：模拟边界验证通过。
- Notes：真实合成笔记保存与读回、保留标签和原文、重复抑制、独立进程复用通过。首次运行约 4.5 秒，独立进程续接约 1.8 秒；补充一条记录并验证保留历史约 7.4 秒。单笔记小样本，不能代表大规模性能。
- 新建正式日志分支仅模拟验证；F101 的 Notes 新建能力已有真实证据，F103 正式文档未创建。
- 每条 4000 字符、笔记 HTML 32768 字符、1000 条操作状态，每次最多 6 次 Notes 调用，每次桥接超时 15 秒；0 次模型调用。超限停止，不截断写入、不自动增建日志文件。
- 每次追加含恢复标识，保存在笔记中供核对；回执预览去掉本功能的恢复标识。
- 同一状态目录串行并有进程占用保护。Notes 无原子条件更新；多设备同时修改、同步延迟、应用重启与真实飞书回执故障未验收。
- `recover:feishu` 仍只恢复原收集流程。OKR 通过重新投递原事件或再次启动来核对；未知写入无法核实时停止，需人工确认外部结果。飞书回执结果未知沿用既有“不自动重发”规则。

规格与测试接口见 [F103 规格](../../.scratch/f103-okr-session/spec.md)，检查结果见 [任务记录](../../.scratch/f103-okr-session/issues/01-session.md)。
