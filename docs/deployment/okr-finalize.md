# F104：OKR 引导与确认定稿

## 行为与用法

F104 在 F103 日志入口上增加模型引导：背景 → 方向与策略 → 年度/季度目标与 KR → 反向审视 → 待确认。每轮最多 1–3 个问题，原回答、阶段、摘要、建议和草案写入日志后再回复。目标与 KR 使用 #O1、#KR1 等直接标记；本次不读写提醒事项标签、不自动评估任务进展。

启用后发送 `小婕 gtd okr 讨论`，回复小婕的消息逐轮讨论。收到完整草案后，**回复那条草案回执“确认定稿”**，才更新最新完整稿。回复自己的原消息、旧草案、其他会话或只发送未关联的确认均不能定稿。“好的”等普通表达继续讨论，不代替确认。改动或模型失败后的新记录会使旧草案失效。

最多两篇备忘录：

- `PGTD OKR 日志`：原回答、建议、待确认草案、确认请求和旧版。
- `PGTD OKR 最新稿`：最后一次明确确认的完整目标稿；首次定稿时创建，以后按同一真实 ID 更新。

模型草案仍可能补充需要核对的细节。最新稿是用户接受的目标，不代表指标已经达成。Review 分析和任务标签查询留待 F105–F109。

## 配置与运行边界

沿用 [F103 配置](okr.md)。运行适配器为 OKR 注入 `model.discussOkr`，与普通收集共用 `usagePath` 和调用/金额上限，没有新增服务或依赖。未配置 `okr` 时不访问 Notes；本轮未改动运行配置、未重启网关、未发送飞书、未推送。

- 一条新回答最多一次模型请求；重投、超时与重启均不重调同一条。模型失败保留原回答，阶段不推进。
- Gemini `maxOkrOutputTokens` 默认 4096；超时继承模型配置，业务等待最长 15 秒。最多传入最近日志 3000 字符、最新稿 8000 字符、用户 4000 字符；输入总字节仍受 `maxInputBytes` 约束，超限停止模型请求并记录原文。最新稿被截断时不接受 ready 草案。
- 每篇 HTML 上限 32768 字符，单草案最多 6000 字符，1000 条事件状态。普通轮次最多 8 次 Notes 调用，确认最多 12 次；每次 15 秒。容量不足停止，不自动建第三篇笔记。
- 共享账本保存调用数、token、延迟、费用估算及失败原因，不含正文。此次真实测试消耗 4 次调用；测试结束时既有 45 次额度已用 44 次，没有重置或扩大授权预算。部署或继续真实模型测试前需要核对剩余额度。

## 写入与恢复

确认使用已显示的草案，不再次生成。先向日志追加确认内容与旧版，再创建/替换最新稿。写前保存意图，成功后读回；日志成功而最新稿失败时不声称定稿成功。结果未知时，重投原确认只核对标记，不盲目重写。未解决的定稿操作阻止其他新轮次。

确认前比较最新稿与生成草案时的快照。人工编辑后拒绝覆盖；追加日志和替换最新稿也比较写前 HTML。Notes 没有原子条件更新，多设备同步竞态仍未验收。保留 `okr.sqlite`，不能通过删状态或换目录处理未知结果。

`recover:feishu` 仍只处理收集流程；OKR 需重投原事件核对。日志中的“用户确认定稿”记录确认请求，实际当前稿以最新稿为准。
