# OKR 持续回复修复（2026-10-01）

## 原因与修改

用户反馈持续回复原 OKR 回执后出现通用“请求未确认完成”。只读核对两条失败消息：身份、会话和父回执一致，飞书 API 都标记 updated=true，更新时间分别比创建时间晚111ms和271ms。原代码在进入 OKR 模块前统一拒绝 updated 消息，插件把 invalid_source 转成通用错误。两条失败输入没有进入模型或 Apple 写入；不能据此推断 provider 为何设置 updated。

现在只对已绑定同用户、同会话的 OKR 普通讨论回复，在可信事件与 API 正文完全一致、且未出现同ID改文时允许处理。普通收集、显式命令、确认定稿、暂停仍保留编辑保护。正文不同会明确提示以新消息回复原 OKR 对话，不调用模型或写备忘录。不会把消息正文和用户身份写进诊断日志。

未形成草案也保存累积事实与上轮问题，传回模型；重新进入时接着当前问题。grilling 方法保持每轮一个核心决定，可在同一 O/KR 上停留多轮，不因收到一次回答就推进；用户指出旧目标为测试内容时，不继续当成个人承诺。完成后仍需明确确认定稿。

## 验证与范围

`node --test --test-name-pattern='OKR回复原回执' test/feishu.test.js` 修复前重现 invalid_source，修复后通过。连续15轮回复同一旧回执、中途重启、同事件重投，恰好15次模型调用和15次记录，未进入 Inbox。

`node --test --test-name-pattern='草案尚未形成' test/okr.test.js` 修复前复现重新追问周期，修复后通过。另验证正文不一致、同ID改文、编辑确认仍不执行。完整 `npm test` 132项通过。

本次不删除原测试历史，不新增笔记，不增加既有55次/$0.5预算。持续讨论没有固定的轮数限制，但仍受剩余模型额度、单条输入和笔记容量限制；不能宣称无限讨论。

## 真实恢复与网络验证

按原消息实际ID恢复第一条被拒绝回复，保存原文一次；未重放第二条重复内容。第一次模型请求直连超时（network_or_timeout），原文降级保存且阶段不推进。只读网络检查发现本机启用127.0.0.1:7897系统代理，Node直连超时、通过代理可达。

用一次稳定恢复事件仅补充下一轮质询，没有再次追加用户原回答；沿用该回复的业务内容，真实模型返回 direction，继续厘清策略路径，事实摘要和当前问题均已保存。两次尝试都计入共享用量，49/55次，剩余6次；0.5美元上限不变，超时调用保持未知费用预留，不重置账本。本次不向飞书主动发消息。

网关 LaunchAgent 增加 HTTPS_PROXY（现有系统代理）、NODE_USE_ENV_PROXY=1、NO_PROXY=localhost,127.0.0.1,::1，保留私有原plist备份；重新bootstrap使环境生效。这会让该网关的外部HTTPS请求使用现有本地代理，依赖代理进程在线，网关重装后应复核该设置。未改系统代理或凭据。

`npm run check`、`demo:okr`、`demo:okr-finalize`、`demo:feishu`、`plugin:validate`及`git diff --check`通过。实际飞书原消息读取和模型/Notes恢复已验证；新飞书事件在部署后的端到端回执待用户验收。

顺序审查：规范维度核对同用户/会话/真实ID、编辑保护、未知费用、数据不入Git；需求维度核对原回执续接、多轮同一问题、重启后事实/问题保留及技能与提示一致。未删除用户历史或自动定稿。
