## Problem Statement

用户希望在飞书中快速收集任务、想法和文章链接，保留原始表达，并在明确指定时间时获得提醒。普通讨论不应变成任务；分析或网络失败不能悄悄丢失内容、重复创建或产生虚假成功回执。

## Solution

在消息开头使用可配置的默认激活词“小婕 GTD”，通过明确的自然语言收集或提醒指令，将一条内容写入 Apple 提醒事项 Inbox。列表不存在时创建。事项保留原文，备注包含一句“小婕的建议：……”；用户明确要求的提醒时间设置在同一事项上。

首版实现 GTD 收集与初步处理建议。文章链接只保存，不读取网页；用户后续自行将同一条目移入 Apple 的 Wiki 待处理列表。独立 Wiki agent 的读取与归档属于未来版本。

## User Stories

1. 作为用户，我希望一句明确指令就能保存想法、任务或资料链接，避免再次手动录入。
2. 作为用户，我希望原文完整保留，并看到一句署名“小婕的建议”的处理建议，以便之后厘清。
3. 作为用户，我希望指定时间后在同一事项上设置提醒，避免一件事出现两个条目。
4. 作为用户，我希望时间不明确时先收集，再补齐时间，不丢失事项。
5. 作为用户，我希望普通聊天和未确认的裸链接不会自动写入。
6. 作为用户，我希望分析失败仍能收下明确要求保存的原文，并准确知道提醒是否已经设置。
7. 作为用户，我希望重复投递、服务中断或回执失败不会重复创建同一请求的事项。

## Implementation Decisions

### 已确认的输入与行为

- 新请求通过消息开头的激活词单次激活；正文或引用中出现激活词不触发。未激活的新消息返回未处理，由现有入口继续路由。
- 激活词存于本地配置，修改后重启生效；本版不新增设置网页或聊天修改命令。
- 输入仅限文字和消息内链接，包括粘贴正文；图片、语音、附件、转发消息卡片暂不处理，并明确反馈支持范围。
- 激活后明确的“收集”“记录”“提醒我”等自然语言意图可直接执行；只有链接时询问是否收集；询问文章看法不自动收集或触发全文读取。
- 一次收集创建一条事项，不自动拆成多条行动。原文与模型建议分开保存；不能把模型建议当作用户承诺。
- 文章链接和普通收集项一样进入 Inbox，首版不执行自动移动、飞书移动指令或 Wiki 写入。
- 默认时区为 Asia/Shanghai，可配置；显式时区优先。相对日期以原消息发送时间为依据，不能因延迟或重试改成处理当天。
- 时间不明确时先保存无提醒时间的事项，再追问。补齐时间后更新同一 Apple 对象，不重新创建。
- 澄清回复无需激活词，但必须关联到原请求。后续消息不能仅因存在某个待澄清项就被误当作它的回答。
- 用户已确认：指定提醒时间已经过去时，先保留事项、不设提醒，询问新的时间；不自动顺延或立即提醒。

### 最小输入输出接口（已确认的验收边界，字段细节由实现落实）

主要入口接收规范化消息事件：稳定的消息 ID、发送者与会话 ID、发送时间、消息类型、原始文字、回复关联信息，以及可信的本地配置。配置、权限和消息元数据不能从消息正文中获取权威值。

输出包含处理状态、关联原消息的信息、拟发送回执，以及成功写入时的真实列表 ID 和事项 ID。处理状态应区分：未处理、待确认收集、已收集、已收集待补时间、提醒已设置、已收集但分析未完成、暂不支持、明确失败、结果待核对。

回执里的“已收集”“提醒已设置”必须有 Apple 成功结果支持；回执发送失败不应回滚或重新创建已成功的事项。每次重试以真实 ID 和原请求标识核对状态，不能只按标题匹配。

### 必要的内部职责（实现建议）

- 飞书/OpenClaw 接入负责消息来源、身份与授权校验、事件转换及回执发送。
- 收集流程负责激活、意图处理、原文保留、时间澄清与结果状态。
- 模型接入只返回受校验的分析结果；权限、输入限额、重试和实际写入由代码控制。
- Apple 接入负责列表绑定/创建、事项创建、读取核对及更新提醒时间。
- 最小持久化操作记录负责去重、待澄清关联与重启恢复；不建立另一套权威任务状态。

首次绑定列表时若出现多个同名候选，要求明确选择目标 ID；不能随意写入。账户和列表实际 ID 需接入时确定，测试使用合成数据。

待澄清回复建议优先依靠明确的回复关联；无关联且无法唯一定位时先询问，不修改任何条目。具体飞书元数据支持情况需检查本地已安装接入能力。

## Failure Handling

| 情况 | 对外行为与恢复要求 |
| --- | --- |
| 明确收集指令的模型分析失败或超时 | 在可确认收集意图且 Apple 可用时保存原文，标明分析未完成，不编造建议或时间；无可靠标题时使用确定性的原文摘要标题，备注保留完整原文 |
| 收集意图本身无法可靠判断 | 先询问，不靠模型猜测制造用户承诺 |
| 提醒时间不精确或有歧义 | 已收集但未设提醒，追问后更新同一对象 |
| Apple 明确拒绝写入 | 报告未成功及可采取的下一步，不声称已保存 |
| 创建列表、创建事项或更新时间后响应丢失 | 记录结果未知；先核对外部状态，再决定是否重试；无法判定时停止新增写入 |
| 已创建事项但提醒设置失败 | 明确区分已收集和提醒未设置；保留 ID，后续只修复该对象 |
| Apple 写入成功但飞书回执失败 | 保留写入结果，后续补回执；不重复创建事项 |
| 同一事件重复投递或并发到达 | 在创建前用稳定事件身份去重，创建结果可重复查询；标题相同不代表同一事件 |
| 写入后进程重启 | 从最小操作记录和外部状态恢复，不盲目重新创建 |
| 输入超过已验证容量 | 明确报告并请求拆分输入，不静默截断原文、不谎称完整保存 |
| 调用预算耗尽 | 保存已有进度，停止新增调用，回执反映实际已完成部分 |

以上为对已确认失败原则和项目工程约定的具体化；容量阈值、外部核对能力与持久化方案需接入验证后确定。

## Testing Decisions

### 已确认的主要测试接口

从“接收消息事件”这个公开入口输入合成消息；检查公开处理结果、用户可见回执，以及 Apple 接入边界暴露的列表和事项状态。测试不依赖内部函数调用次数或私有数据结构。

首版目前没有现成业务接口或测试套件。实现时逐项 TDD：一个失败行为测试、最少实现、再验证下一项。模拟外部服务用于控制超时、重复投递、部分成功和恢复情景；真实 Apple 与飞书接入单独验收，模拟通过不能替代真实验证。

模型质量使用合成表达样例单独评估：收集与讨论区分、提醒时间抽取、建议一句话且不增加承诺。模型桩只用于确定性业务流程测试，不能作为模型理解正确的证据。

### 可观察验收样例

时间样例固定消息发送时间为 2026-09-27 10:00 Asia/Shanghai。

| 输入或场景 | 可观察预期 |
| --- | --- |
| `小婕 GTD，收集：研究家庭网络升级` | Inbox 恰有一条新事项，保留原文；分析正常时备注有一句“小婕的建议：……” |
| `小婕 GTD，提醒我明天下午三点交报价` | 同一条 Inbox 事项设置 2026-09-28 15:00 Asia/Shanghai 提醒；回执包含明确日期、时间及对应时区 |
| 上一条消息次日才被处理或重投 | 仍解析为 2026-09-28 15:00，不按处理日重新计算；过去时间的处置需在时间规则中验证，不能改成未来日期 |
| `小婕 GTD，提醒我下周找老王聊一下` | 先创建一条无提醒时间的事项，回执说明待补时间；明确关联回复后只更新该条 |
| `小婕 GTD，收集：https://example.org/article` | 保存原消息和链接，不读取网页、不创建 Wiki 来源卡、不移动条目 |
| `小婕 GTD，https://example.org/article` | 询问是否收集，确认前不创建；明确关联确认后创建一次 |
| `小婕 GTD，这篇文章怎么样：https://example.org/article` | 不自动写入；GTD 收集流程不读取文章全文 |
| 普通聊天或正文引用激活词 | 不进入收集写入流程 |
| 激活后发送不支持的内容 | 明确提示支持范围，不用空内容创建事项 |
| 配置新激活词并重启 | 新词可用，旧词不再作为新请求激活词；未完成的澄清关联仍按原请求核对 |
| 模型分析失败 | 明确收集的原文仍可保存，用户看到分析未完成；不生成虚构建议或提醒时间 |
| 重复投递、结果未知、部分成功、重启 | 对同一事件最多创建一个事项，状态和回执与实际结果一致；无法核实时不盲目重试 |

## Cost and Performance Budget

用户未指定费用和延迟数值。以下是实现前用于验证的工程候选值，不是已测性能或用户已承诺预算：

| 项目 | 候选约束 / 待测项 |
| --- | --- |
| 模型调用 | 每个入站事件最多 1 次分析调用，模型自动重试 0 次；重复投递复用已有结果；澄清回复视为独立事件 |
| 模型超时 | 候选 15 秒；超时走已确认的降级路径 |
| 输入规模 | 候选每条最多 8,000 Unicode 字符；需实测飞书、模型和 Apple 备注容量后确定最终上限 |
| 模型输出 | 候选最多 512 token，只生成必要结构与一句建议；用户原文由代码直接保存 |
| 外部重试 | 候选同一操作最多 2 次尝试；写入未知时先核对，不能因剩余预算直接重试 |
| 测量条件 | 候选至少 30 条合成消息，覆盖普通收集、链接、时间和澄清；固定机器、模型版本与网络条件，报告各类数量、p50/p95 延迟及失败率 |
| 延迟目标 | 待真实接入测量后设定；不能用模型超时数值代替整条链路性能目标 |
| 金额预算 | 模型及价格来源验证后计算；单次与累计金额上限待配置，真实模型运行前落实 |

每次模型调用记录模型标识、调用量、输入/输出 token、延迟和失败原因；不记录私人正文。Apple 调用、回执和整条处理链路也需有明确超时和尝试上限，具体值在依赖验证后固定，不能无限等待。

- 自动抓取文章全文、Wiki 来源卡/知识文章生成、独立 Wiki agent 的执行与调度。
- 自动拆分任务、自动移动分类、飞书修改/删除/完成任务指令。
- GTD 完整组织体系、Review、早晚简报、OKR 关联、邮件与日历接入。
- 持续激活模式、设置 UI、多 Agent 平台、通用插件框架。

### 06 交付范围调整（2026-09-27）

用户要求本轮完成 06 的代码与交接，由管理 OpenClaw 的另一个 agent 安装和调试。因此本轮交付可安装插件、离线验证及安装验收清单；真实飞书闭环与性能仍由安装方执行，不据模拟结果勾选首版整体验收。

公开测试接口沿用已确认的可信事件入口与外部服务边界：OpenClaw `reply_dispatch` → 飞书原消息查询/回执 HTTP → 持久化收集 → Apple 适配。测试替换外部服务，不替换业务内部函数。按本机 2026.9.6 SDK 实现，使用 Feishu 原消息的类型、原文、发送时间、发送者和父消息关联；拒绝身份不一致、编辑、删除的消息。不会读取文章 URL。

本轮固定工程上限：每事件模型最多一次、15 秒；飞书每次 HTTP 10 秒且无自动重试，响应最多 128 KiB；收集外部操作 20 秒；排队最多 16 个请求、最多 1000 个事件；回执响应未知时不自动重发。真实延迟/容量及长期运行费用预算由安装验收另行确认，本轮不新增付费调用。
