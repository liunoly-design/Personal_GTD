# F104：OKR 引导、策略审视与定稿

基准：`26d3296faeea131f89010b4c252015df76741294`。

## 目标与范围

在 F103 固定日志上，引导背景 → 方向与策略 → 逐个年度/季度 O/KR → 反向审视 → 待确认。模型每轮围绕一个决定，1–3 个问题；用户回答与建议、草案、阶段一起写日志，保存后才显示下一轮。最多两篇 Notes：日志与最新完整稿。#O1/#KR1 等标签直接写文档，不建映射库。

只有显式“确认定稿”且关联当前待确认草案才能更新最新完整稿；普通“好的”、沉默及模型确认声明均不触发。草案需年度/季度周期、目标、KR、可验证成功标准/基线或未知、资源、策略比较、反对理由与待决项。自动 Review 与事项标签接入不在本任务。

## 输入输出、接口与规则

- `openOkrSession.handle` 扩展 confirm 动作；同一可信用户/会话的关联回复进入讨论。`openFeishuCapture.handle` 负责验证原消息、关联确认与回执。
- `openGeminiAnalyzer.discussOkr` 复用调用账本，接收最近日志、当前完整稿、当前阶段和用户回答，返回结构化 stage/summary/advice/questions/draft。代码验证长度、阶段及草案标签；模型无工具和写入权限。
- 开始背景问题无需模型；后续每次回答最多一次模型请求。阶段只能原地、前进一步或退回重谈，不能从背景跳到待确认；进入待确认前必须有用户对反向审视的回应。
- 待确认回执附带草案版本，确认必须关联该版回执；后续回答产生新草案会使旧确认失效。确认时使用已展示的文本，不重新生成。
- 模型不可用/预算耗尽仍保存用户原文，说明未推进分析；同一事件重投不重调模型。保存失败先核对，不继续新轮次。
- 首次定稿创建最新完整稿，以后按真实 ID 替换；先在日志保存确认及旧版，再更新最新稿。部分成功保留状态，重投原确认恢复；不重复创建笔记、不覆盖人工修改。

## 预算

复用 Gemini 的共享 token/费用/延迟/失败原因账本；最多一次调用/新回答、无自动重试、超时继承配置（默认15秒），OKR 输出上限4096 token。输入沿用 maxInputBytes，传入日志末尾最多3000字符、完整稿最多8000字符、用户4000字符；超限停止模型调用并保存原文。日志和最新稿各32768 HTML字符；草案正文最多6000字符。普通轮次最多8次 Notes 调用，确认恢复最多12次，每次15秒。模拟单轮目标<1秒；真实模型/Notes性能待测。

逐项 TDD：结构化模型边界、业务会话及飞书公开接口。合成验证正常多轮、不同策略/反向审视、明确确认、旧版/跨会话确认拒绝、重复事件、重启、模型失败、人工编辑、日志成功最新稿失败及未知结果恢复。执行完整测试和运行示例。真实模型质量与 Apple 双笔记写入分别报告，未获得新增真实笔记授权时仅复用已有合成笔记验证日志；不部署/发送飞书。
